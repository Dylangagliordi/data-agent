## 1. State Schemas

### `SQLAnalystState` — `models/schema.py`

Shared state threaded through every node of the SQL analyst LangGraph.

| Field | Type | What it holds |
|---|---|---|
| `messages` | `list` (add_messages) | Accumulated LangChain messages (HumanMessage / AIMessage) |
| `user_question` | `str` | Raw question string from the user |
| `curated_question` | `str` | Grammar/spelling-corrected question (no intent change) |
| `prompt_query_context` | `str` | Full schema context string built by add_context for the LLM |
| `generated_sql_query` | `str` | SQL text produced by generate_sql (may be updated on retry) |
| `is_safe` | `Literal["yes","no"]` | Safety judge verdict |
| `comments` | `str` | Safety judge reasoning text |
| `sql_query_execution_result` | `str` | Structured JSON `{"columns":[...],"rows":[[...],...],"truncated":bool}` for successful queries, or error string prefixed `SQL_EXECUTION_ERROR:` |
| `final_answer` | `str` | Plain-English answer (set by represent_final_answer, cancel_sql, or build_visualization) |
| `data_quality_warnings` | `list` | List of `{"table": str, "warning": str}` dicts for fail-level or no-record tables |
| `sql_attempts` | `int` | Count of generate→execute cycles; capped at `MAX_SQL_ATTEMPTS = 5` |
| `data_quality_action` | `Literal["proceed","needs_cleaning"]` | Set by add_context; "needs_cleaning" routes to clean_and_reload |
| `tables_to_clean` | `list` | List of `{"table": str, "source_folder": str}` dicts for tables that need auto-cleaning |
| `cleaning_attempted_tables` | `list` | Table names already attempted this question (stop condition for clean loop) |
| `wants_visualization` | `bool` | True only when the router dispatches to visualize_node |
| `chart_type` | `str` | e.g. "bar chart", "scatter plot", "treemap" |
| `chart_type_source` | `Literal["explicit","reasoned"]` | Whether the user named the chart type or the LLM chose it |
| `chart_type_reasoning` | `str` | Non-empty only when `chart_type_source == "reasoned"` |
| `output_file_path` | `str` | Absolute path to the written CSV file |
| `export_target` | `Literal["csv","tableau"]` | "tableau" only when curated_question explicitly names Tableau |
| `chart_image_path` | `str` | Absolute path to the rendered `.png` file (empty string if rendering failed or not a visualization run) |
| `chart_category_column` | `str` | Set by `resolve_chart_columns` (visualization path, after execute_sql succeeds): the REAL result column name to use as the chart's category/x-axis, resolved by meaning rather than SQL SELECT-list position. Blank when resolution was skipped (empty/truncated result). |
| `chart_value_column` | `str` | Set by `resolve_chart_columns`: the REAL result column name that is the metric the question actually asked about — fixes a real bug where a chart plotted `cols[1]` positionally (e.g. `avg_salary`) instead of the column the question meant (e.g. `avg_rating` for a satisfaction question). |
| `chart_secondary_column` | `str` | Set by `resolve_chart_columns`; only meaningful when `chart_type` is "stacked bar" or "treemap" (the sub-category/nested dimension) — empty string for every other chart type. |
| `chart_column_resolution_note` | `str` | Non-empty only when `resolve_chart_columns` had to fall back to its deterministic heuristic instead of a confident LLM pick (LLM error, or an invalid/non-real column returned). Appended to `final_answer` by `build_visualization`, same pattern as `disclosure_note`. |
| `chart_type_override_note` | `str` | Set by `validate_chart_shape` when `chart_type` had to be overridden against the REAL result (e.g. a pie chart with >5 categories, a line chart with a non-temporal category column) — empty string when no override was needed. Appended to `final_answer` by `build_visualization`. |
| `transformation_narrative_log` | `list` | Populated by `surface_transformations` (Spec 2, Part B narration source). One entry per real `TransformationCandidate` actually surfaced and decided THIS question: `{"table_name", "candidate" (dict), "chosen_option_id", "reasoning_shown" (the real context/options shown), "fresh" (True if decided during this call, False if pulled from the `_transformation_decisions` cache), "reload_reask" (True only when `fresh` is also True AND this table was actually cleaned/reloaded earlier in this same run — never inferred from cross-session log archaeology), "decided_at" (the cached decision's real timestamp when `fresh` is False, else `None`)}`. Accumulates across repeat calls within one run (no LangGraph reducer) rather than being overwritten. `utils/narrative.py:build_narrative_walkthrough` reads this straight off the logged `query_log.jsonl` entry. **Spec 3:** `reasoning_shown` takes a SECOND possible shape for a manual-mode-resolved decision — `{"source": "manual_mode", "reference": <the real ManualModeOverride.reference_source>, "supplied_data": <the real mapping applied>}` — instead of the normal `{"context", "options"}` shape; `fresh` is always `True` for these (never asked live this call, but never pulled from a prior cached decision either), `reload_reask` always `False`. `utils/narrative.py:_add_transformation_step` checks `reasoning_shown["source"]` to render these distinctly. |
| `transformation_candidates_not_relevant` | `list` | Populated alongside `transformation_narrative_log`: every real stored `TransformationCandidate` for a touched table that `surface_relevant_transformations` did NOT surface this question. Each entry: `{"table_name", "candidate" (dict)}`. Used by `build_narrative_walkthrough` for the low-emphasis "other optional transformations exist" note (Part B, item 7). |

**Auxiliary structured-output schemas (not in main state):**
- `JudgeSchema` (`models/schema.py`): `answer: Literal["yes","no"]`, `comments: str` — used by `is_safe` node only.
- `ChartTypeSchema` (`models/schema.py`): `chart_type: str`, `chart_type_source`, `chart_type_reasoning` — used by `determine_chart_type` node only.
- Dynamic per-call chart-column schema: `agents/sql_analyst.py:_build_chart_column_schema(columns)` builds a Pydantic model (via `pydantic.create_model`) whose `category_column`/`value_column`/`secondary_column` fields are typed as `Literal[...]` over the ACTUAL result column names present in that call's query result — structurally prevents the LLM from inventing a column name. Used only by `resolve_chart_columns`.
- `CategoricalAssignment` / `CategoricalConsolidationProposal` (`models/schema.py`, Spec 3, Part 2): `assignments: list[CategoricalAssignment]` (each `{raw_value: str, group: str}`) — used only by `utils/categorical_consolidation.py:_generate_categorical_consolidation_mapping`'s live AI-clustering call. A list of pairs rather than one big `dict[str,str]` field, for reliability over a large (dozens-of-entries) mapping; the caller mechanically verifies the response covers every real distinct value before trusting it.

| Field | Type | What it holds |
|---|---|---|

## 2. Log File Formats

### `logs/query_log.jsonl`

One JSON line per run. Shape varies by `route_response`.

**`sql_analyst` entry keys:**
```
timestamp, route_response, route_comments, user_question,
curated_question, generated_sql_query, is_safe, comments,
sql_query_execution_result, final_answer,
transformation_narrative_log, transformation_candidates_not_relevant
```

**`visualize` entry keys** (superset of sql_analyst, adds visualization fields):
```
timestamp, route_response, route_comments, user_question,
curated_question, chart_type, chart_type_source, chart_type_reasoning,
generated_sql_query, is_safe, sql_query_execution_result,
output_file_path, chart_image_path, final_answer,
transformation_narrative_log, transformation_candidates_not_relevant
```
`chart_image_path` is present and non-empty when `build_visualization` succeeded; empty string when rendering failed. Entries logged before the image-rendering feature (commit c9ebda2) lack this key entirely — report code treats its absence as "no image available".

`transformation_narrative_log` / `transformation_candidates_not_relevant` (Spec 2, Part B narration source) are read directly off `SQLAnalystState` — see their entries under `SQLAnalystState` and `surface_transformations` below. Entries logged before Spec 2 lack these keys entirely; `utils/narrative.py` treats their absence as "nothing to narrate for Part B" (`.get(..., [])`), never an error.

**`etl_analyst` entry keys:**
```
timestamp, route_response, route_comments, user_question, final_answer
```

`sql_query_execution_result` is a structured JSON string `{"columns":[...],"rows":[[...],...],"truncated":bool}` for successful queries (Decimal serialized as float, datetime as ISO string). Errors are an unquoted string prefixed `SQL_EXECUTION_ERROR:`. Old log entries (pre-security-hardening commit) may contain the legacy `str()` repr or `[TRUNCATED TO FIRST …]` format.

**Written by:** `main.py:log_run()`. SQL/visualize internal fields come from `result.get("sql_analyst_trace", {})` — the `DataAgentSchema.sql_analyst_trace` field `sql_node`/`visualize_node` return as part of their own node output (see `DataAgentSchema` above; not a module-level global).

### `logs/cleaning_log.jsonl`

One JSON line per `clean_dataset()` call.

**Top-level keys:**
```json
{
  "timestamp": "2026-09-02T20:05:07.031931+00:00",
  "source_folder": "data/data-science-jobs",
  "trigger": "manual",
  "files": [ ...file_rec objects... ]
}
```
`trigger` values: `"manual"` (clean_data.py or direct call), `"auto_redirect"` (clean_and_reload node in sql_analyst graph).

**Per-file record (`file_rec`) keys:**
```json
{
  "file_name": "Uncleaned_DS_jobs.csv",
  "table_name": "Uncleaned_DS_jobs",
  "status": "cleaned",
  "issues_found": [{"issue": "Placeholder values: ...", "severity": "fail"}, ...],
  "row_count_before": 672,
  "row_count_after": 672,
  "row_loss_flagged": false,
  "issues_resolved": ["Placeholder values: ...", ...],
  "issues_still_unresolved": [],
  "fail_issues": [{"issue": "...", "status": "resolved", "reasoning_comments": ["# comment"]}],
  "fail_batches": [{"issues": [...], "signature": ["placeholder", ["-1"]], "status": "resolved", "reasoning_comments": [...]}],
  "warn_batches": [{"issues": [...], "status": "resolved", "reasoning_comments": [...]}, ...]
}
```
`status` values: `"cleaned"`, `"skipped_declined"`, `"skipped_no_issues"`, `"skipped_no_llm"`.
`table_name` uses the original CSV stem (not necessarily lowercase) — report code normalizes to lowercase when looking up DB tables.

**Spec 4 (issue batching) note:** `fail_issues` now holds only UNGROUPED fail-level issues (one entry per issue, unchanged shape) — any 2+ fail-level issues sharing an identical, mechanically-verified treatment signature (see `_issue_treatment_signature`) are pulled out into their own `fail_batches` entries instead (new key; `"signature"` is `_signature_to_jsonable`'s plain-list form of the Python tuple, e.g. a frozenset payload becomes a sorted list — `None` is never possible here since only signature'd groups become batches). `warn_batch` (singular) is GONE — replaced by `warn_batches` (plural list, possibly empty `[]`, never `null`): a file can now have more than one, since Spec 4 carves a separate batch out for any 2+ warn issues sharing a real signature, while everything else (no signature, or a signature unique among that file's warn issues) is still pooled into one final combined batch — the pre-Spec-4 default preserved for anything that isn't a genuine multi-issue match. An issue lives in exactly one of `fail_issues` / `fail_batches` / one `warn_batches` entry, never more than one.

**Written by:** `utils/data_cleaning.py:_append_cleaning_log()`.

### `_data_quality_status` Postgres Table

Created and maintained by `utils/load_data.py:ensure_data_quality_status_table()`.

```sql
CREATE TABLE _data_quality_status (
    table_name   TEXT PRIMARY KEY,
    last_loaded_at TIMESTAMPTZ NOT NULL,
    status       TEXT NOT NULL,          -- "pass", "warn", or "fail"
    issues_found JSONB NOT NULL,         -- list of {"issue": str, "severity": str}
    was_cleaned  BOOLEAN NOT NULL,
    source_folder TEXT,                  -- added after initial schema; NULL = can't auto-redirect
    source_checksum TEXT                 -- added for source-freshness tracking; NULL = no baseline
);
```

`status` is set by `utils/load_data.py:compute_quality_status()` which calls `_issue_severity()` from `utils/data_cleaning.py`. The table is excluded from `information_schema` queries in `add_context` (filtered by `table_name NOT IN ('_data_quality_status', '_fanout_status', '_transformation_candidates', '_transformation_decisions', '_derived_columns')` — the last three added by Spec 1; omitting an internal table from this list makes it appear as an ordinary queryable table and triggers a spurious "has no recorded data-quality check" warning on every question, a real bug hit and fixed while building Spec 1). Only `fail`-status tables inject WARNING lines into `generate_sql`'s context; `warn`-status tables are silently ignored.

`source_checksum` is the raw source file's real SHA-256 hex digest at the time it was last processed (`utils/load_data.py:compute_file_checksum`). Compared against the file's current bytes by `check_source_freshness()`, called from three places: `add_context` (every table with a known `source_folder`, regardless of current status — architecture review point #22), `clean_and_reload` (per targeted table, informational logging only, since those tables are already being reloaded regardless), and `load_data.py:main()` (per file, informational logging only). In `add_context`, a genuine mismatch on a `"pass"`/`"warn"`-status table is a real gate: it forces `tables_to_clean`/`"needs_cleaning"` exactly like a `"fail"` status would, with a `"...source changed, forcing fresh clean."` warning — a stale status row is never silently reused once its source file has actually changed. See "Auto-cleaning/reload hardening" below.

### `_fanout_status` Postgres Table

Created and maintained by `utils/load_data.py:ensure_fanout_status_table()`. Written by `compute_and_write_fanout_status()` after every table load. Read by `add_context` via `_read_fanout_from_metadata()` in `agents/sql_analyst.py`.

```sql
CREATE TABLE _fanout_status (
    table_name   TEXT NOT NULL,
    column_name  TEXT NOT NULL,
    is_likely_fk BOOLEAN NOT NULL,
    has_fanout   BOOLEAN NOT NULL,
    source       TEXT NOT NULL,    -- 'declared_pk', 'declared_fk', 'cardinality_heuristic'
    checked_at   TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (table_name, column_name)
);
```

One row per id-like column per table. `source` indicates how the determination was made:
- `'declared_pk'`: column appears in an `information_schema` PRIMARY KEY constraint — not a FK, no fan-out.
- `'declared_fk'`: column appears in an `information_schema` FOREIGN KEY constraint — is a FK; cardinality checked for `has_fanout`.
- `'cardinality_heuristic'`: no declared constraint; id-like column checked via `COUNT(*)/COUNT(DISTINCT)`. Unique → inferred PK (is_likely_fk=False). Non-unique → inferred FK (is_likely_fk=True, has_fanout=True).

`add_context` reads precomputed rows instead of running live cardinality scans per question. Tables not in `_fanout_status` fall back to live `_detect_fanout_warnings` and log a message to stderr. SELECT granted to `app_reader` by `ensure_fanout_status_table`.

### `_transformation_candidates` / `_transformation_decisions` Postgres Tables (Spec 1, Parts 0/1)

Both created/maintained by `utils/load_data.py` (`ensure_transformation_candidates_table` / `ensure_transformation_decisions_table`, SELECT granted to `app_reader`). Together they back the **Transformation Options** phase — see `utils/transformation_options.py` below — a second, human-in-the-loop pipeline phase for judgment-call enrichment/style decisions, kept structurally separate from `clean_dataset()`'s fully-automatic Phase 1.

```sql
CREATE TABLE _transformation_candidates (
    table_name  TEXT PRIMARY KEY,
    detected_at TIMESTAMPTZ NOT NULL,
    candidates  JSONB NOT NULL     -- list of TransformationCandidate dicts
);

CREATE TABLE _transformation_decisions (
    table_name       TEXT NOT NULL,
    candidate_id     TEXT NOT NULL,
    chosen_option_id TEXT NOT NULL,
    reasoning_shown  JSONB NOT NULL,  -- {"context": {...}, "options": [...]} shown at decision time
    decided_at       TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (table_name, candidate_id)
);
```

`_transformation_candidates` holds the FULL current candidate list for a table, replaced wholesale (never merged) by `write_transformation_candidates` every time `detect_transformation_candidates()` runs — which is exactly once per genuine fresh load/reload, wired into both `utils/load_data.py:main()` (manual CLI load) and `agents/sql_analyst.py:clean_and_reload` (auto-clean redirect), immediately after `load_csv_to_table` + `compute_and_write_fanout_status` succeed for that table. `_transformation_decisions` is the durable decision cache: `invalidate_cached_decisions_for_table` is called at the same two reload sites right after re-detection, clearing every previously-cached decision for that table (Part 0's reload-invalidation rule — never guesses whether an old decision still applies to possibly-different underlying data).

**Both tables are excluded from `add_context`'s `information_schema` schema-context query** in `agents/sql_analyst.py` (the same `table_name NOT IN (...)` filter that already excludes `_data_quality_status`/`_fanout_status`) — without this exclusion they'd appear as ordinary queryable tables and trigger a spurious "has no recorded data-quality check" warning on every question (a real bug hit and fixed while building this feature).

### `_cleaning_recipes` Postgres Table (Spec 7: Cleaning Recipe Cache)

```sql
CREATE TABLE _cleaning_recipes (
    table_name     TEXT NOT NULL,
    signature_hash TEXT NOT NULL,
    signature      JSONB NOT NULL,
    generated_code TEXT NOT NULL,
    approved_at    TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (table_name, signature_hash)
);
```

One row per `(table_name, signature_hash)` — a previously human-approved fix for a signature-eligible fail/warn issue group (one of the six `_issue_treatment_signature`-defined categories: placeholder, currency_unit, spreadsheet_artifact, locale_format, boolean_families, leading_zeros). `signature_hash` is `compute_recipe_id(table_name, signature)` (`utils/data_cleaning.py`) — sha256 over `(table_name, _signature_to_jsonable(signature))`, same reasoning `compute_candidate_id` already documents for why sha256 and not Python's per-process-salted `hash()`. Scoped by `table_name` always, never by signature alone: an identical signature on a *different* table must never reuse this table's recipe (the same cross-table mixup class of bug the dtype-aware signature fix already exists to prevent).

`generated_code` never stores the real, literal `cloned_path` the fix was originally generated against — the code-gen prompt tells the model "read and overwrite this exact path," so the approved code always hardcodes it, and that path is wrong on any later run. It's replaced with `_RECIPE_PATH_PLACEHOLDER` before storage and substituted with the current run's real path immediately before replay — a mechanical string swap, never a rewrite of the fix's actual logic.

**Excluded from `add_context`'s `information_schema` query**, same `table_name NOT IN (...)` list and same reasoning as the other four internal tables above — this exact class of bug (an internal bookkeeping table appearing as an ordinary queryable table, triggering a spurious "no data-quality check on record" warning) has now been hit and fixed four separate times as new internal tables were added; caught proactively this time before shipping, by checking the exclusion list explicitly while building this spec rather than waiting to hit the bug live.

**Live wiring:** `ensure_cleaning_recipes_table` is called at the same two sites as the other `ensure_*` functions (`load_data.py:main()`, `clean_and_reload`), and `invalidate_cleaning_recipes_for_table` is called at the same two reload-invalidation sites as `invalidate_cached_decisions_for_table`, immediately after a genuine reload. `clean_dataset()`'s new `recipe_conn` parameter defaults to `None`, reproducing pre-Spec-7 behavior exactly with zero database dependency — load-bearing, since `clean_data.py`'s entire point is running with no DB connection at all; only `load_data.py:main()` and `clean_and_reload` (which already hold an admin connection for other reasons) actually pass one in.

See `tests/test_cleaning_recipe_cache.py` (live Postgres, fake call-counting LLM, no live model): cache miss generates and saves a recipe, then a cache hit on the same table replays it with zero new LLM calls; an identical signature on a different table triggers a fresh generation rather than reusing the first table's recipe; `recipe_conn=None` never touches `_cleaning_recipes` at all (proven via a monkeypatch that raises if it's ever called); a seeded recipe that runs without error but doesn't actually fix the issue is discarded and falls back to a real, fresh generation rather than being accepted as resolved.

### `_derived_columns` Postgres Table (Spec 1, Part 7)

Created/maintained by `utils/load_data.py` (`ensure_derived_columns_table`, SELECT granted to `app_reader`; also excluded from `add_context`'s `information_schema` query, same reasoning as above).

```sql
CREATE TABLE _derived_columns (
    table_name  TEXT NOT NULL,
    column_name TEXT NOT NULL,
    kind        TEXT NOT NULL,   -- the feature-derivation kind, "range_decomposition", etc.
    derived_at  TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (table_name, column_name)
);
```

One row per column ever added by a Transformation Options fix (feature derivation or range decomposition — `label_simplification` rewrites an existing column in place and adds nothing, so it's never marked here). `mark_derived_columns(conn, table_name, column_names, kind)` upserts; `get_derived_columns(conn, table_name) -> {column_name: kind}` is read by `add_context` (`agents/sql_analyst.py`) and spliced directly into the schema-context line it builds for each column: `- company_age (integer) [DERIVED via company_age — not an observed source value]` — right in the text `generate_sql` reads, so a computed value is never presented, generated against, or disclosed as an originally-observed fact (Part 7's own explicit requirement). See `tests/test_derived_columns.py`.

## 3. Code Organization

### `agents/sql_analyst.py` — SQL analyst graph nodes and helpers

| Function | Role |
|---|---|
| `curate_question` | Node 1: grammar/spelling fix only, no intent change. Uses `pick_llm("cheap")`. |
| `add_context` | Node 2 (no LLM): builds schema context from `information_schema`, runs fan-out check and DQ status check (including a per-table checksum-freshness re-verification — architecture review point #22), sets `data_quality_action`. |
| `determine_chart_type` | Node (visualization path only): classifies chart type via `ChartTypeSchema` with `pick_llm("cheap")`, using an ORDERED priority-list prompt (`DETERMINE_CHART_TYPE_SYSTEM_PROMPT`) — explicit type named > time/trend language > distribution language > part-to-whole language (pie only for ≤5 fixed categories) > two-numeric-measures language > nested-categorical language > default bar. `chart_type_reasoning` must name which numbered rule fired. This runs BEFORE the real SQL result exists, so some of its own rules (e.g. the ≤5-category pie constraint) are unenforceable at this point — see `validate_chart_shape` below, which re-checks against the real result after execute_sql. |
| `generate_sql` | Node 3: writes one SQL query. Uses `pick_llm("high")`. Extended with chart-shaping instructions on visualization path. **Mechanical compliance retry (architecture review point #25):** after the first LLM call, `_min_sample_rule_violated(state.curated_question, sql_query)` checks whether the minimum-sample-size rule (HAVING COUNT(*) >= 5) should have applied but was silently skipped; if so, the LLM is called exactly once more with the concrete violation and the previous query appended to the prompt (same corrective pattern as a real execution-error retry), and the regenerated query is what's returned. A compliant first attempt makes only one LLM call. |
| `is_safe` | Node 4: deterministic AST safety gate (`_ast_safety_check`, authoritative — architecture review point #23) run first; only if it passes does a `pick_llm("cheap")` / `JudgeSchema` call run as a secondary, non-authoritative sanity check whose comments are surfaced but never override an AST-cleared query back to unsafe. |
| `execute_sql` | Node 6: runs SQL via `app_reader`, sets `SET LOCAL statement_timeout` before every query, caps results at `MAX_RESULT_ROWS = 200`, serializes to JSON via `_ResultEncoder` (Decimal/datetime safe), handles errors and retry counting. Uses `conn.rollback()` (never `conn.commit()`) — read-only connection. **Autocommit guard (architecture review point #26):** `SET LOCAL statement_timeout` only binds within an open transaction — under autocommit=True each `cur.execute()` is its own implicit transaction, so the timeout would never bind to the query that follows it. `get_app_reader_connection()` never sets autocommit (psycopg2 defaults to `False`), but `execute_sql` explicitly checks `conn.autocommit` and forces it off if it's ever `True`, rather than only relying on that default. |
| `cancel_sql` | Node 7: writes final_answer explaining blocked query. |
| `represent_final_answer` | Node 8: plain-English summarization via `pick_llm("cheap")`. Bypassed deterministically for truncated results. |
| `resolve_chart_columns` | Node (visualization path only, after `execute_sql` succeeds, before `validate_chart_shape`): resolves which REAL result columns to plot BY MEANING rather than SQL SELECT-list position — fixes a real bug where a chart plotted `cols[1]` positionally (e.g. `avg_salary`) instead of the column the question actually meant (e.g. `avg_rating` for a satisfaction question). Skips entirely (returns `{}`, leaving `chart_*` fields blank) when the parsed result is empty or truncated. ### `utils/data_cleaning.py` — Cleaning core

| Symbol | Role |
|---|---|
| `clean_dataset(folder_path, llm=None, trigger="manual")` | Main public entry point. Accepts `llm=` for test injection of a fake LLM (otherwise calls `pick_llm("high")`). Per file: runs `check_rubric(file_path)`, THEN also runs `explore_and_verify(df, llm=resolved_llm, flagged_columns=_columns_with_fail_issues(static_issues))` on the same DataFrame, capturing BOTH of its return values — `(discovered_issues, pattern_lookup)` — and concatenates `discovered_issues` onto `check_rubric`'s output BEFORE `_split_issues_by_severity` runs — this happens even when `check_rubric` found nothing for a file (that's exactly the case a closed catalog of pattern-matchers can miss; see discovery-phase entries below), so a file only lands in `untouched_files` when BOTH the static rubric and discovery find nothing. `pattern_lookup` is threaded straight through to every fail-level `_clean_issue_group(cloned_path, group, resolved_llm, pattern_lookup=pattern_lookup)` call, so a composite-field issue's fix generation can use the pattern that discovery already verified (see `_clean_issue_group` / `_generate_composite_split_code` below). **Spec 4 (issue batching):** fail-level issues are first grouped via `_group_issues_by_signature(fail_issues)` — a group of 2+ issues sharing an identical, mechanically-verified treatment signature gets ONE combined `_clean_issue_group` call (`-> FailBatchRecord`); everything else (signature `None`, or unique) still goes through the original one-at-a-time path (`-> IssueCleaningRecord`). | `_issue_severity(issue)` | Classifies a single issue string as `"fail"`, `"warn"`, or `"unknown"` by prefix match. |
| `_issue_treatment_signature(issue, df=None)` (Spec 4; dtype-aware since Spec 1 Part 4) | Returns a hashable `(kind, payload)` — or `(kind, payload, dtype_category)` when `df` is given — signature proving two issues need the IDENTICAL fix, or `None` if this category has no defined signature (meaning: never group, always process alone). Defined for exactly six categories: `"placeholder"` (frozenset of tokens, via `_extract_placeholder_tokens`), `"currency_unit"` (frozenset of symbols/suffixes, via `_extract_currency_unit_symbols` — `_check_currency_unit_symbols` was extended by Spec 4 to name the specific symbols/suffixes it found directly in the issue text, e.g. `"...(['$'])"`, since its original message was generic and had nothing to extract), `"spreadsheet_artifact"` (`"formula"` or `"excel_error"`, via `_extract_spreadsheet_artifact_kind`), `"locale_format"` (frozenset of format labels, always `{"US-style","EU-style"}` today, via `_extract_locale_format_pair`), `"boolean_families"` (frozenset of family names, via `_extract_boolean_families`), `"leading_zeros"` (int target length, via `_extract_leading_zero_target_length`). | `_extract_bracketed_quoted_list(issue)` | Shared regex helper (`_BRACKETED_QUOTED_LIST_RE`): pulls a Python-list-repr bracketed, quoted token list embedded as `"(['a', 'b'])"` — the shape both `_check_placeholder_values` and `_check_boolean_inconsistency` already produce via `f"...({sorted(x)})..."`. Used by both `_extract_placeholder_tokens` and `_extract_boolean_families`. |
| `_group_issues_by_signature(issues, df=None)` | Partitions a flat issue list into groups: issues with equal, non-`None` signatures group together (2+ per group); every `None`-signature or uniquely-signed issue becomes its own single-item group. Used directly for fail-level issues; wrapped by `_partition_warn_groups` for warn-level. |
| `_partition_warn_groups(warn_issues, df=None)` | Warn-level counterpart with one deliberate difference from the fail-level function above: any `_group_issues_by_signature` group of size 1 (no real multi-issue signature match) is pooled back into ONE final combined batch — preserving the pre-Spec-4 "always one whole-file warn batch" default, which Spec 4 only carves REAL structure out of, never replaces. `df` forwarded the same way as above. | `_clean_issue_group(cloned_path, target_issues, llm, pattern_lookup=None, recipe_conn=None, table_name=None, signature=None)` | **Spec 7 (Cleaning Recipe Cache):** when `recipe_conn`/`table_name`/`signature` are all given (signature is one of the six `_issue_treatment_signature`-defined categories — composite-field issues never have one, so this never co-occurs with the composite branch), the FIRST attempt tries `read_cleaning_recipe(recipe_conn, table_name, compute_recipe_id(table_name, signature))` before ever calling the LLM or `_request_approval` — the cached code's placeholder path (`_RECIPE_PATH_PLACEHOLDER`) is substituted with the real, current `cloned_path`, then it's executed and re-verified through the exact same checks below as any other attempt. Scoped by `table_name` always — an identical signature on a different table never reuses this table's recipe (same cross-table mixup class of bug the dtype-aware signature fix already exists to prevent elsewhere). Generates and executes fix code for a batch of issues. Calls `_request_approval` for interactive approval gate. Per-attempt re-check has THREE parts: (1) does `check_rubric()` still detect any of this group's target issues (textual re-check, original behavior); (2) if the group contains a `ROW_COUNT_INTEGRITY_PREFIXES` issue, did the file's row count change vs. before this attempt — if so the attempt is rejected as NOT resolved (fed back into the next generation call's `previous_error`) even though the textual check passed; (3) **composite-field shape check**: when `target_issues` is a single `"Composite field (discovered):"` issue (always the case in practice — composite-field issues are fail-level, so `clean_dataset` always processes them one at a time, never batched), part (1) above is structurally vacuous — `check_rubric()` has NO code path that can ever reproduce a `"(discovered)"` string, so `still_present` is trivially always `[]` for this issue type regardless of whether the fix actually did anything. `_composite_split_shape_ok` is the REAL check here: compares the file's columns before vs. after and requires the originally-flagged column gone AND exactly 2 brand-new columns — anything else (dropped with no replacement, 3+ new columns) is rejected with `f"Expected exactly 2 replacement columns after composite-field split, found {n}."`, overriding what would otherwise be returned as `"resolved"`, and retrying (feeding that reason back as `previous_error`) up to `MAX_CLEAN_ATTEMPTS` same as the other two checks. Code generation itself branches on issue text: a singleton `"Composite field (discovered):"` issue with a real entry in `pattern_lookup` routes to `_generate_composite_split_code` (the one narrow, explicitly-scoped exception permitted to add/drop columns); everything else — including a composite-field issue whose `pattern_lookup` entry is missing (logged via `print(..., file=sys.stderr)`, never raises) — still goes through the unchanged, general-purpose `_generate_cleaning_code` / `CLEANING_CODE_SYSTEM_PROMPT`. **Legitimate decline (Spec 2.1):** immediately after generating composite-split code, `_extract_no_split_reason(code)` checks for the `NO_SPLIT` sentinel — if present, returns `"declined_false_positive"` right away with NO retry, NO execution, and NO approval prompt at all (`_request_approval` is never even reached). This is deliberately NOT fed into the retry loop as a failure: doing so was the original hole Spec 2.1 closed — a shape-check failure ("expected 2, found 0 — try again") could otherwise pressure the model into fabricating a shape-compliant-but-meaningless split just to satisfy the check's letter, a concrete instance of the same failure class this project already hit twice before (truncation-fabrication, ranking-convention variance): a mechanical check with no legitimate "doesn't apply" escape hatch eventually gets gamed. |
| `_composite_split_shape_ok(original_columns, current_columns, flagged_column)` | The real post-fix verification for a composite-field split (see `_clean_issue_group` above) — `check_rubric()`'s generic re-check cannot provide it for this issue type. Returns `(ok, reason)`; `ok` requires the flagged column absent from `current_columns` AND exactly 2 columns present that weren't in `original_columns`. |
| `_COMPOSITE_FIELD_PREFIX` | `"Composite field (discovered):"` — used by `_clean_issue_group` to detect when the single-narrow-exception routing/shape-check applies. |
| `COMPOSITE_FIELD_SPLIT_SYSTEM_PROMPT` | The one explicitly-scoped exception to `CLEANING_CODE_SYSTEM_PROMPT`'s "never add/drop columns" rule — permits splitting the flagged column into EXACTLY TWO new, descriptively-named columns using the already-verified pattern, dropping the original, touching nothing else, and leaving non-matching rows null rather than fabricating a value. Leads with an explicit, first-class decline path (Spec 2.1): if the real sample values show the pattern match was a false positive (a sequential ID, a coincidental match, or a split that would produce two meaningless fragments), the model is instructed to output exactly `"# NO_SPLIT: <one-sentence reason>"` and nothing else — framed explicitly as a successful outcome it will not be asked to retry, not a failure. **Discovery-phase config constants** (`utils/data_cleaning.py`, near `MISSING_VALUE_THRESHOLD`): `EXPLORE_SAMPLE_SIZE = 40`, `EXPLORE_RARE_VALUE_FRACTION = 0.5`, `EXPLORE_MAX_COLUMN_PAIRS = 10`, `EXPLORE_MAX_LLM_CALLS_PER_TABLE = 60`, plus private thresholds `_EXPLORE_PROSE_MEAN_LEN_THRESHOLD = 200`, `_COLUMN_PAIR_OVERLAP_THRESHOLD = 0.95`, `_EXPLORE_MIN_COLUMN_ROWS = 20`.

**Known trade-off (observed live, not hypothetical):** a live run of `explore_and_verify` against the real `Uncleaned_DS_jobs.csv` correctly caught the `Company Name`/rating composite bug (93% real match), but also produced a few weak/false-positive "composite field" hypotheses on other columns (e.g. an `index` column matching a trivial `^\d+$`/`^.+$` pattern — not real evidence of two glued-together values). A plain sequential/unique-id-like column (name matching `UNIQUE_ID_NAME_HINTS`-style heuristics, or just any all-digit identifier) is a particularly reliable false-positive magnet for this reason — it trivially satisfies almost any narrow all-digit regex at 100%. This is an accepted trade-off, not a bug in discovery itself: the actual safety net is the human approval gate `_clean_issue_group` already routes every fail-level issue through.

**Downstream consequence, observed live after the composite-field FIX PATH was added, since CLOSED by Spec 2.1:** with a real LLM and `_generate_composite_split_code` wired in (see `_clean_issue_group` above), a false-positive "id column is composite" discovery no longer just got a harmless declined/no-op comment — the composite-specific shape check (`_composite_split_shape_ok`) REJECTED a no-op "no real split exists" response (0 replacement columns ≠ 2) and fed that back as `previous_error`, which could pressure the LLM into fabricating a semantically meaningless but SHAPE-COMPLIANT split on a later retry (e.g. splitting a plain integer id into `id_first_digit` / `id_remaining_digits`) purely to satisfy "exactly 2 new columns" — and that WOULD have been accepted as `"resolved"` since it structurally satisfied the shape check, even though it wasn't a genuine fix. This was a real, live-observed interaction between the discovery false-positive risk and the shape-check's retry pressure — not a bug in the shape check itself (it was doing exactly what was specified: verify shape, not semantics), but the same failure class this project has hit twice before (truncation-fabrication, ranking-convention variance): a mechanical check with no legitimate "doesn't apply" escape hatch eventually gets gamed by whatever's under pressure to satisfy it.

**Spec 2.1 closed this with two changes together (neither alone would have been enough):** (1) `_is_sequential_id_like_column` skips the single most common false-positive shape (a plain sequential id) before discovery ever proposes a hypothesis for it at all — see `explore_column`/`explore_and_verify` above; (2) `COMPOSITE_FIELD_SPLIT_SYSTEM_PROMPT` now leads with an explicit `NO_SPLIT` decline sentinel, and `_clean_issue_group` treats a decline as an immediate, terminal, successful outcome (`"declined_false_positive"`) — NOT fed back into the retry loop, so the fabrication-under-pressure path can never be reached even for a false positive that (1) doesn't catch (a different column shape, or a shape that's genuinely ambiguous). Confirmed live and in `tests/test_composite_field_decline.py`: a legitimate decline makes exactly one LLM call, never reaches `_request_approval`, and leaves the file completely untouched.

| `read_cleaning_recipe(conn, table_name, signature_hash)` (Spec 7) | Returns `{"generated_code", "approved_at"}` or `None` if this exact `(table_name, signature_hash)` has never had an approved fix recorded (or was invalidated). | `invalidate_cleaning_recipes_for_table(conn, table_name)` (Spec 7) | `DELETE FROM _cleaning_recipes WHERE table_name = %s` — wired into the exact same two reload sites as `invalidate_cached_decisions_for_table`, same reload-invalidation reasoning: never guess whether an old recipe still applies to possibly-different underlying data. |
| `_is_id_like_column(col)` | Returns True for `'id'` or any column ending in `'_id'`. Used by `compute_and_write_fanout_status`. |
| `compute_quality_status(unresolved_issues)` | Returns `(status, issues_found_payload)` using `_issue_severity` from `data_cleaning.py`. Status: `"fail"` > `"warn"` > `"pass"`. |
| `write_data_quality_status(conn, table_name, status, issues_found, was_cleaned, source_folder=None, source_checksum=None)` | Upserts one row in `_data_quality_status`. `source_checksum` is the raw source file's SHA-256 at processing time (see below); `None` means "no baseline". |
| `read_data_quality_status(conn, table_name)` (Spec 2) | Returns `{"status", "issues_found", "was_cleaned", "last_loaded_at"}` for `table_name`, or `None` if it's never been processed by the loader/cleaning pipeline at all. Used by `utils/data_dictionary.py`, which must never fabricate a "pass" default for a table with no recorded status. |
| `compute_file_checksum(path)` | Real SHA-256 hex digest of `path`'s bytes, streamed in 1 MiB chunks. |
| `get_stored_checksum(conn, table_name)` | Returns the `source_checksum` last recorded for `table_name`, or `None` if there's no row yet or the column is `NULL`. Commits immediately after the SELECT to release its lock (same pattern as `_fetch_status` in `tests/test_auto_clean_redirect.py`). |
| `check_source_freshness(conn, table_name, csv_path)` | Returns `(source_changed, current_checksum)`. `source_changed` is `True` only when a prior checksum exists AND differs from the file's current bytes — a table with no baseline yet is never reported as "changed". Called by `add_context` (real gate for non-`"fail"`-status tables — architecture review point #22, see the `_data_quality_status` section above), `clean_and_reload` (per targeted table, informational only — those tables are already being reloaded regardless of this result), and `load_data.py:main()` (per file, informational only). All three log `[checksum] source changed, forcing fresh clean for '<table>' (...).` to stderr/stdout when a mismatch is detected — see architecture review points #20/#22. |
| `_create_and_populate_table(conn, table_name, csv_path, sample_rows_for_typing=500)` | Low-level create+populate primitive (CREATE TABLE + batched INSERT from the CSV). Raises on any failure (malformed row, type mismatch); never commits — callers own the transaction. Used internally by `load_csv_to_table` to build the staging table. |
| `_swap_table_atomically(conn, staging_name, table_name)` | Atomic swap: any existing `table_name` is renamed to `table_name_previous` (kept, never dropped) before `staging_name` is renamed to `table_name`. Runs inside the caller's still-open transaction — no commit here. `ALTER TABLE ... RENAME` is atomic DDL in Postgres, so `table_name` is never observably missing or half-populated. |
| `load_csv_to_table(conn, csv_path, sample_rows_for_typing=500)` | Loads a CSV into Postgres **atomically** (architecture review point #20): builds a staging table (`_create_and_populate_table`) inside one transaction, then swaps it into place (`_swap_table_atomically`); a single `conn.commit()` at the end covers both steps. Any exception during staging triggers `conn.rollback()` and re-raises — the existing `table_name` (if any) is never touched. Staging table name is deterministic (`__reload_staging__<table_name>`, not random), so an orphaned staging table from a crashed prior load self-heals via the `DROP TABLE IF EXISTS` at the start of `_create_and_populate_table`. Returns `(table_name, row_count)` — same contract as before. |
| `rollback_table(conn, table_name)` | **Manual, deliberate** recovery: swaps `table_name` and `table_name_previous` back (a real swap via a temporary holding name, not a destructive overwrite — the bad version becomes the new `_previous`). Returns `True` if a rollback happened, `False` if there was no `_previous` to roll back to. Nothing in this codebase calls this automatically. |
| `sanitize_identifier(name)` | Lowercases and strips a CSV stem to make a valid Postgres identifier (used as table name). |

### `utils/run_comparison.py` — Run comparison / diff (Spec 4)

### `utils/freshness_briefing.py` — Freshness / drift briefing (Spec 5)

A proactive, all-tables-at-once view of whether each table's real raw source file has changed since it was last processed — the same checksum `_data_quality_status.source_checksum` already records, just checked across every tracked table instead of only reactively, per-question, one table at a time. A detection/reporting signal only, exactly like `check_source_freshness` itself — nothing here triggers a re-clean automatically. Not schema-drift detection (column structure changing over time) — that's a distinct, unbuilt feature; this is specifically about the raw file's bytes.

| Function | Role |
|---|---|
| `get_freshness_briefing()` | One entry per table with a recorded `source_folder` in `_data_quality_status` (a table with none is never included — there's nothing to compare it against). Reverse-maps each table back to its real CSV via `agents.sql_analyst._find_source_csv` (reused, same discipline as Spec 4's `_parse_sql_result` reuse) and compares current vs. stored checksum. Three honest outcomes, never fabricated: `changed=True` (real drift), `changed=False` (unchanged), or `source_file_found=False` with `changed=None` (file can't be located at all — genuinely unknown, never defaulted to "unchanged"). Ranked changed-first, then "can't tell", then unchanged. |
| `render_freshness_briefing_html()` | Renders the briefing as a plain HTML page under `freshness_briefing/freshness_briefing_<timestamp>.html`. |

**CLI trigger** (in `main.py`): `python main.py "freshness"`.

### `utils/sql_transform_extraction.py` — Question-specific SQL shaping (shared)

Public API: `extract_question_transformations(sql_query: str) -> dict`, `has_any_transformation(transformations: dict) -> bool`.

Deterministic (no LLM) parse of a single generated SQL query, used by BOTH `generate_report.py` (`_section_question_transformations`) and `generate_presentation.py` (`_slide_question_shaping`) so this nontrivial parsing logic has exactly one implementation — unlike the small, cheap result-row/column helpers those two modules deliberately keep as independent copies. Separates the transformations unique to shaping data for a SPECIFIC business question from the general, dataset-wide cleaning already tracked in `cleaning_log.jsonl`.

Returns a dict with:
- `cte_steps` — ordered CTE names from a leading `WITH` clause, extracted paren-depth-aware (`_extract_cte_names`) so a comma inside a nested `AS (...)` body never miscounts as a CTE separator.
- `computed_columns` — `[{"alias", "expression"}, ...]`, one per real `<expr> AS <alias>` SELECT-list item (across every CTE and the final query, deduped by alias) that has real arithmetic/`CASE`/aggregate structure — a bare column passthrough (`SELECT industry AS industry`) is excluded via `_BARE_COLUMN_RE` + `_ARITHMETIC_RE`.
- `grouping_columns` — one list of column names per distinct real `GROUP BY` clause, paren-depth-aware split (`_split_top_level`) so `AVG((a+b)/2.0)` in the SELECT list doesn't confuse the parser.
- `having_threshold` — the `N` from `HAVING COUNT(*) >= N`, or `None`.
- `ranking_stages` — `[{"order_by", "limit"}, ...]`, one per real `ORDER BY` clause in appearance order — a query that ranks-and-caps in an intermediate CTE then re-sorts in the final `SELECT` produces two stages.
- `scope_filters` — plain-English topic-scope descriptions from `ILIKE`/`LIKE` pattern matches and positive `=`/`IN` filters against real literals. Deliberately EXCLUDES `IS NOT NULL`/`IS NULL` checks and placeholder `<>`/`NOT IN` exclusions (`_PLACEHOLDER_LITERALS`) — those describe general data-quality cleaning, not this question's specific scope, and are already covered by Part A of the narrative walkthrough (see `utils/narrative.py` below). (Spec 2 removed `generate_report.py`'s standalone `_extract_query_assumptions` — this kind of non-obvious-filter disclosure now lives in `entry["final_answer"]` itself, via `agents/sql_analyst.py:_analyst_judgment_disclosure`, which the walkthrough's `"The final result"` step quotes verbatim.)

`has_any_transformation(t)` is `True` iff any of the above fields is non-empty/non-None — callers use it to render an honest "no additional shaping was needed" note (report) or skip the slide entirely (presentation) for a plain passthrough query, rather than showing an empty section.

### `utils/narrative.py` — Shared narrative walkthrough (Spec 2, Final)

Public API: `NarrativeStep` (dataclass: `step_number`, `part` — `"cleaning"`|`"transformation"`|`"analysis"` — `title`, `explanation`, `technical_detail=""`, `stats={}`), `build_narrative_walkthrough(entry: dict) -> list[NarrativeStep]`, `narrate_steps(steps, llm) -> list[NarrativeStep]`, `assemble_full_walkthrough(entry: dict, llm) -> list[NarrativeStep]`.

**The single source of truth both `utils/generate_report.py` and `utils/generate_presentation.py` render from** — replaced each document's previously-independent section/slide assembly, so the two always agree in sequence and content and differ only in HTML-vs-slide formatting.

`build_narrative_walkthrough(entry)` is a PURE, deterministic function — no LLM call, cheap to call repeatedly, trivially unit-testable. It builds real facts only, in this fixed order:
- **Part A — Data Cleaning** (`part="cleaning"`), per touched table (detected from `generated_sql_query` against live `information_schema`, own copy of the table-detection/metadata helpers — same convention already used independently by `generate_report.py`/`generate_presentation.py` before this spec): a `"Load <table>"` step (real row/column counts) or a `"No cleaning history — <table>"` step; then every fail-level issue in `cleaning_log.jsonl`'s real found-order — a `FailBatchRecord` renders as ONE combined step naming every covered column (`_extract_batch_columns`, tolerant of both the plain `column '<name>'` issue-text shape and the bracketed `across [...]` shape a few whole-file checks use) and the real shared reason (`_describe_signature`, one phrase per of the six defined signature kinds); a singleton `"Composite field (discovered):"` issue renders via `_add_composite_step` with the real match %/pattern parsed out (`_COMPOSITE_RE`) plus an honest, ALWAYS-included caveat that discovery isn't blanket coverage (skips already-fail-flagged/prose/sequential-id columns) — the actual new column names are only stated when `_diff_composite_split_columns` can cleanly isolate them (current cleaned CSV vs. its one kept `.previous` generation shows exactly the flagged column gone and 2 new ones with nothing else changed); every other fail issue is a plain singleton step. Then every warn-level issue/batch, same treatment. Then ALWAYS a `"Duplicate-row check — <table>"` step (real count found + resolved/unresolved, or an honest "found none" when no `"Duplicate rows:"` issue exists) — `"Duplicate rows:"` issues are excluded from the generic fail-issue loop above and rendered exclusively here, never twice.
- **Part B — Transformation Options** (`part="transformation"`): one step per entry in `entry["transformation_narrative_log"]` (written by `agents/sql_analyst.py:surface_transformations`, see `SQLAnalystState` above). `_add_transformation_step` branches on `reasoning_shown["source"]`: for a normal live/cached decision — states what was found, what options were presented (verbatim from the real `reasoning_shown`), what was chosen, and EXPLICITLY that no reason beyond the choice itself was recorded (true today for every live decision — `present_transformation_options` never records a free-text "why", only `chosen_option_id`); states honestly whether the decision was fresh this run, reused from the cache (with its real `decided_at`), or a reload re-ask (only ever claimed when `state.cleaning_attempted_tables` proves this table was actually reloaded earlier in THIS SAME run). **Spec 3:** for `reasoning_shown["source"] == "manual_mode"` — a completely different narration, NEVER the "no reason was recorded" framing (the reference citation IS the reason): states plainly the decision was pinned directly to the supplied reference, names it, and (when `supplied_data` is a mapping) how many assignments across how many groups; sets `stats["manual_mode"]=True` / `stats["reference_source"]` for the checklist (Part 4) and rendering to pick up. If `entry["transformation_candidates_not_relevant"]` is non-empty, one final LOW-EMPHASIS note (`stats["low_emphasis"] = True` — rendered as a plain note, not a numbered step, in both documents) lists every known-but-unsurfaced candidate. Part B is omitted entirely (no steps at all) when both lists are empty.
- **Part C — Analysis** (`part="analysis"`): a `"Shape the data for this question"` step wrapping `utils/sql_transform_extraction.extract_question_transformations` (CTE steps, computed metrics, grouping, `HAVING` threshold, ranking, scope filters) with an honest "used the source data directly" statement when `has_any_transformation` is False — ALWAYS present, never omitted, per Spec 2's "render every step" rule; a `"The final result"` step that quotes `entry["final_answer"]` verbatim (same "don't re-synthesize, quote the one real computed answer" discipline as the pre-Spec-2 report) and carries the real result table in `stats`; a `"Visualize the result as a <chart_type>"` step when `entry["chart_type"]` is set, stating the real `chart_type_reasoning` when `chart_type_source == "reasoned"` or a plain "you asked for a ..." statement when `"explicit"`, plus any real `chart_type_override_note`/`chart_column_resolution_note`.

`narrate_steps(steps, llm)` is the LLM narration pass (Spec 2, section 2) — ONE combined structured-output call (`explanations: list[str]`, Pydantic) per document, using `NARRATIVE_WALKTHROUGH_PROMPT` (kept verbatim as specified) to rewrite every step's `explanation` into first-person "student explaining to a professor" prose. Validates the returned list's length against the input; on any mismatch, malformed response, or exception, falls back to the ORIGINAL deterministic explanations for every step (never drops a step, never partially narrates). `title`/`technical_detail`/`stats` are never touched by narration — only `explanation`.

`assemble_full_walkthrough(entry, llm)` is what both documents actually call: `build_narrative_walkthrough` → `narrate_steps`, THEN folds in two Part C additions Spec 2's own "Explicitly out of scope" section keeps as-is ("the glossary/second-chart presentation additions already working well — keep those, fold their existing output into Part C") — moved here (previously presentation-only) so both documents render them:
- `resolve_category_values(entry)` / `generate_glossary(category_label, values, llm)` → a `"What do these categories mean?"` step inserted immediately BEFORE the chart step, when the result has a resolvable non-numeric category column and the glossary LLM call succeeds.
- `resolve_scatter_columns(entry)` / `render_scatter_chart_png_b64(resolved)` → a `"Scatter, sized by volume"` step inserted immediately AFTER the chart step, when the real result has a category column, a count-like column, and 2+ other numeric measures.

Both are appended AFTER `narrate_steps` runs (each already produces its own natural-language/rendered content via its own dedicated call, so neither is narrated a second time) and the whole list is renumbered into one contiguous sequence.

### `utils/generate_presentation.py` — HTML slideshow generator

Public API: `generate_presentation(entry: dict) -> str` (returns path to written `.html`).

Writes vanilla-JS slideshows to `presentations/<slug>_<timestamp>.html`. Slide 1 is a lightweight title slide (question + touched dataset names + generated-at timestamp). Every slide after that renders `utils.narrative.assemble_full_walkthrough(entry, pick_llm("cheap"))`: a section-divider slide at the start of each `part` (`Part A: Data Cleaning` / `Part B: Transformation Options` / `Part C: Analysis` — omitted for a part with zero steps, e.g. Part B on an entry with nothing surfaced), **immediately followed by one checklist-style slide for that part** (`_slide_checklist`, Spec 3 Part 4 — built from `utils.manual_mode.build_step_checklist`, `None`/omitted when the part has zero steps), then one slide per `NarrativeStep` — `_slides_for_step` splits a step across multiple slides only when its `explanation` exceeds 120 words (`_split_words`), reusing the step's real `stats` (result table, chart image, glossary table, scatter chart — all base64/inline, no re-fetching) only on the LAST chunk so heavy content isn't duplicated across a split step's slides. The low-emphasis Part B note renders as a smaller, muted-styled slide (no numbered "Step N:" heading), never omitted. Falls back to the plain deterministic `build_narrative_walkthrough(entry)` (no LLM) if `assemble_full_walkthrough` itself raises.

JS navigation: `show(n)`, ArrowRight/ArrowLeft keyboard support, `show(0)` on load. HTML attribute IDs use double quotes (`id="prev"`, `id="next"`, `id="counter"`).

**CLI triggers** (in `main.py`):
- `python main.py "present last"` — builds slideshow from most recent `query_log.jsonl` entry without re-running the query.
- `python main.py "present: <question>"` — runs the question fresh, then builds a slideshow from that run's log entry.

### `utils/generate_report.py` — HTML report generator

Public API: `generate_report(entry: dict) -> str` (returns path to written `.html`). `last_query_log_entry() -> dict | None`.

The ENTIRE report body is `utils.narrative.assemble_full_walkthrough(entry, pick_llm("cheap"))` rendered as HTML (falls back to the plain deterministic `build_narrative_walkthrough(entry)` if that raises) — one `<h1>Part A: Data Cleaning</h1>` / `<h1>Part B: Transformation Options</h1>` / `<h1>Part C: Analysis</h1>` each time `step.part` changes, **immediately followed by a compact checklist table** (`_checklist_html`, Spec 3 Part 4 — built from `utils.manual_mode.build_step_checklist`, empty string/omitted when the part has zero steps), then `<h2>Step N: <title></h2>` per step. `_step_html(step)` additionally renders: a collapsible `<details>`/`<summary>Real, verbatim detail behind this step</summary>` block whenever `step.technical_detail` is non-empty (the raw issue text, SQL, or decision JSON — supports the "spot-check against the raw log" acceptance-test discipline even after the LLM narration pass has rewritten the prose above it); the real result table for the `"The final result"` step; the real chart image for the `"Visualize the result as a ..."` step; the glossary table for `"What do these categories mean?"`; the scatter chart for `"Scatter, sized by volume"`. The low-emphasis Part B note renders as a plain `<div class='note'>`, never a numbered `<h2>`.

The report's `<title>`/`<h1>` prefers `curated_question` over `user_question` (falls back to `user_question` only if `curated_question` is absent) — `user_question` still carries any router prefix (e.g. `"Visualize: "`) verbatim, which reads poorly when hard-truncated to 60 chars; the output filename slug still uses `user_question`/`curated_question` fallback unchanged.

### `utils/llm_pick.py` — Model tier routing

`pick_llm(level)` returns a chat model:
- `"cheap"` → `ChatAnthropic(model="claude-haiku-4-5", temperature=0)` — curate_question, is_safe, represent_final_answer, router_node, determine_chart_type, resolve_chart_columns, ETL call_model. (`validate_chart_shape` is pure Python — no LLM call at all.)

### `utils/system_map.py` — Live system self-map (Spec 1)

Renders the real, currently-compiled structure of any of this project's three LangGraph graphs, replacing three checked-in PNGs (`sql_analyst_graph.png`, `etl_analyst_graph.png`, `data_agent_graph.png`) that used to be hand-regenerated and silently went stale — confirmed live: the checked-in `sql_analyst_graph.png` was missing `surface_transformations`, `resolve_chart_columns`, and `validate_chart_shape`, all added to the real graph after the image was last regenerated by hand.

| Function | Role |
|---|---|
| `generate_system_map(graph_name)` | Imports and compiles `graph_name` fresh (never a cached reference) — one of `"sql_analyst"`, `"etl_analyst"`, `"data_agent"` — and returns its real, current structure as mermaid-rendered PNG bytes via LangGraph's own `graph.get_graph().draw_mermaid_png()`. ## 4. Database Structure

**Two-role setup:**
- `app_reader` — DB-enforced read-only (SELECT + USAGE only; INSERT/UPDATE/DELETE/TRUNCATE/CREATE revoked at the database level — see AGENTS.md invariant). All graph runtime queries use this role (`utils/db.py:get_app_reader_connection()`). Never re-add write grants — the LLM safety judge is a UX layer, not the security boundary.
- Admin/superuser — write access. Used exclusively by `utils/load_data.py:get_admin_connection()`. Also used by `clean_and_reload` node (which calls `load_data.py` functions).

**Severity mapping location:** `utils/data_cleaning.py` — `FAIL_LEVEL_PREFIXES` and `WARN_LEVEL_PREFIXES` tuples at module level (lines 177–208). `compute_quality_status` in `utils/load_data.py` calls `_issue_severity` imported from `data_cleaning.py` — same mapping, one source of truth.

**Output directories:**
- `outputs/visualizations/` — CSV and PNG files from `build_visualization`. Naming: `{40-char-slug}_{YYYYMMDD_HHMMSS}.{csv,png}`. Tableau also writes a `.hyper` file alongside the CSV.
- `reports/` — HTML reports from `generate_report`. Naming: `{40-char-slug}_{YYYYMMDD_HHMMSS}.html`.
- `presentations/` — HTML slideshows from `generate_presentation`. Same naming convention.
- `logs/` — `query_log.jsonl` and `cleaning_log.jsonl`.

**Analyst judgment rubric:** `analyst-judgment-rubric.md` at the project root documents all 14 rules enforced by `GENERATE_SQL_SYSTEM_PROMPT` and the disclosure helpers. Rules 1–8 and 12 have post-execution disclosure via `_analyst_judgment_disclosure`; Rules 9–11, 13, and 14 are prompt-only enforcement. Rule 14 (NULL-filter placement for per-category rankings — all `IS NOT NULL` filters feeding a ranking metric must live in one `WHERE` clause in the base CTE, before `GROUP BY`) is regression-tested live in `tests/test_null_filter_placement_consistency.py`.

## 5. Testing Conventions

**File naming:** `tests/test_<feature>.py` — standalone executable scripts, not pytest. Run with `PYTHONPATH=/path/to/data-agent uv run python tests/test_<feature>.py`.

**`_llm=None` / `llm=None` injection pattern:** Both `clean_dataset(folder_path, llm=None, ...)` and `clean_and_reload(state, _llm=None)` accept a fake LLM object in tests. When `None` (always in production), they call `pick_llm("high")`. Tests pass deterministic fake LLMs (e.g. `FakeDedupLLM`, `AlwaysFailLLM`, `AnyCodeLLM`) to control code generation without live API calls. Used in: `test_auto_clean_redirect.py`, `test_data_cleaning_retry.py`, `test_data_cleaning_post_validation.py`, `test_data_cleaning_fail_warn_split.py`, `test_data_quality_status.py`, `test_visualize_auto_clean.py`, `test_reload_hardening.py`. `clean_dataset` passes this SAME resolved LLM straight through to `explore_and_verify(df, llm=resolved_llm, ...)` (not a separate `pick_llm("cheap")` instance) — a pre-existing fake that only implements plain `.invoke()` (no `.with_structured_output`) triggers an `AttributeError` inside `explore_column`/`_verify_hypothesis`/`_explore_column_pairs`, but each of those catches it (`except Exception`) and treats it as "nothing noticed", so every one of the fakes above keeps working unmodified — discovery just silently contributes zero extra issues for those tests, exactly matching pre-discovery-phase behavior. `explore_column`/`_verify_hypothesis`/`_explore_column_pairs`/`explore_and_verify` themselves default to `pick_llm("cheap")` when called directly with no `llm=` at all (see `test_data_cleaning_discovery.py`'s `DispatchLLM` fake, which DOES implement `with_structured_output`, for the discovery phase's own dedicated tests).

**Data fixtures:** Test data lives under `data/_test_etl/` — separate subdirectory per scenario (`clean_only/`, `dq_fail/`, `dq_warn/`, `approve_yes/`, `reload_hardening/`, `checksum_gate/`, etc.). Tests that require interactive approval (`test_data_cleaning_approve.py`) require stdin to be piped — they fail with `EOFError` when run non-interactively; this is expected behavior, not a regression.

**Simulating an interactive session for `clean_and_reload` (architecture review point #24):** `clean_and_reload` checks `sys.stdin.isatty()` before doing anything else and fails closed if it's `False` — but a piped `printf 'yes\n' | ...` stdin (used throughout this suite to script approval answers) is never a tty either, even though `input()` reads the piped lines successfully. Any test that calls `clean_and_reload` directly and needs it to actually proceed (not fail closed) must wrap the call in `with patch("sys.stdin.isatty", return_value=True):` (from `unittest.mock`) — see `test_auto_clean_redirect.py`'s `approve`/`decline` scenarios, `test_reload_hardening.py`'s `clean` mode, and `test_visualize_auto_clean.py`. This check lives in `clean_and_reload` itself, not in `utils/data_cleaning.py:_request_approval` — that function is shared by manual CLI cleaning (`clean_data.py`, `utils/load_data.py`) and most of the test suite, both of which legitimately pipe answers to a non-tty stdin and must NOT be gated.

**Mode-based test files:** A few test files take a CLI arg to select which scenario(s) to run, because different scenarios need different (or no) piped stdin — see each file's own docstring for the exact `printf` invocation per mode:
